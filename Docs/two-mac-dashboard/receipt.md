## Resource measurements

Values below use decimal MB and CPU seconds divided by real elapsed seconds; 100% is one core. See [numeric observations](measurements.json). The benchmark used an isolated Chrome profile, a temporary instrumentation flag in each dashboard runtime, Darwin process accounting, and no video launches. No system-wide before/after load difference was attributed to the dashboard.

| Scenario | Observation |
|---|---|
| Baseline | 125 s with a blank browser. No active dashboard worker or collections. Chrome itself already used substantial memory. |
| Normal visible cadence | Final build: three completed observations per Mac, 60.38 and 60.30 s apart. Across the two steady intervals (120.69 s), M6 worker plus SSH client used 0.0655 CPU-s (0.054% of one core). M2 collector plus the two SSH session processes used about 0.2144 CPU-s (0.178%). Both are below 0.5%. |
| Cold start / steady memory | First measured process startup and refresh: M6 0.100 CPU-s including the client, M2 about 0.094 CPU-s. M6's warm worker footprint was about 16.7 MB. M2 had no dashboard worker between requests. |
| Refresh peak | Approx. **37 MB footprint**: M6 worker ~16.8 MB and SSH client ~2.9 MB; M2 collector ~10.4 MB, user SSH session ~2.7 MB, privileged session ~4.1 MB. Sum of measured component peaks, not an exact simultaneous high-water mark. Sum using RSS instead: **about 64 MB**, above 50 MB. RSS includes shared pages. The estimated incremental footprint meets the goal; a hard sub-50-MB aggregate RSS cap does not. |
| Browser, separately | One visible dashboard added about **28–50 MB** to the isolated Chrome process group's physical footprint versus its blank view in two runs (late, matched samples). One 125 s visible run used 0.335 browser CPU-s in total (0.27% of one core). In steady matched samples, CPU differed from blank by at most about 0.04 percentage point in the late matched windows; browser housekeeping makes a precise page-only CPU delta unreliable. The browser cost is not included in the backend target. |
| Two visible windows | Browser-reported visible in both. A second visible view reused the reading, with one collection per host per normal interval; repeated manual requests coalesced in fixtures. Two visible views used more browser RAM, without creating a second backend or remote collector. |
| Hidden and closed | In separate 125 s Chrome phases collection counters stayed unchanged. The M6 worker was absent by the end of both phases. A return from hidden triggered a new successful per-host reading. A GET-only layout check around the hidden/return boundary did not initiate collection. |
| M2 timeout and recovery | Three one-minute-spaced failed SSH probes to an isolated loopback endpoint, no change to M2 or the user's networking. The test's 1.2 s wall limit terminated and reaped the SSH child. M6 readings completed in 11–14 ms while M2 was pending. During the three failed intervals M6's isolated harness plus SSH used roughly 0.029 CPU-s over 180 s (0.016%), ~21.6 MB process peak RSS plus ~3.8 MB child peak; no remote process was created. Reconnection used the real M2 successfully. A separate test seeded with the live successful cache confirmed the exact prior success timestamp survived failure and advanced only at recovery. |

The first pass included 125 s each for one and two visible windows; the service was updated during that two-window pass. The steady CPU result comes only from the final uninterrupted run. Optimizations after the initial observations: skip Python's unused site setup in both runtimes, and resolve missing titles for M2 using M6's existing catalog cache. Initial M2 collector peak RSS was about 17 MB, final about 15 MB. A macOS-specific timer correction preserves cache age across worker exits. The normal user does not run the profiler.

Memory limits: physical footprints are sampled or reconstructed from the maximum seen per component. The inaccessible privileged SSH session was measured with macOS top on two equivalent fresh M2 connections (4,048 KiB each); its RSS was measured on the actual connections. M2 CPU is sampled immediately before disconnect; remote interpreter and SSH teardown are not fully measurable, and the privileged process time is rounded to hundredths of a second. Collector/client RSS includes startup; browser group totals include browser, renderer, GPU and utility processes and can vary by profile. These short, real-workload windows are evidence, not a performance guarantee.
