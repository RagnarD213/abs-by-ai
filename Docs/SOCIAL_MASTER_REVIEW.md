# Master social inventory and daily review

The private master inventory retains every imported placement without a storage entry cap. Blotato remains the posting service and holds at most 200 queued platform entries across all accounts. The inventory is separate from that limit. Media references, captions, approval evidence, collection snapshots, database files and receipts stay outside the public repository.

The first import reads the complete live Blotato schedule and the approved studio-photo plan. A live schedule is recorded as an observed scheduled placement, with its source ID and collection time. It does not establish original approval or permission to recreate a missing post. The October 3 studio handoff explicitly approves its 27 posts, with 54 platform placements. Drafts outside that evidence are not promoted to approved content.

Every placement retains platform, account, exact authorized date, caption, media, cover, content kind and provenance. Imports are idempotent. Blotato re-hosts media per post, so the studio import joins a live placement only when its account, platform, caption and time agree and every uploaded image's SHA-256 matches the approved manifest. Ambiguous collisions stay separate for review. Their original evidence is retained even after a verified alias joins them.

The Mac uses a private SQLite inventory. The website has an additive PostgreSQL mirror in `brief_social_master`, behind the existing Google owner gate. Signed edition publication accepts optional `socialMasterImports` batches of up to 100 records. This bounds a request, not inventory storage. Repeat batches upsert the same identities; they never truncate the inventory. The normal edition excludes these import batches after validation. The owner can browse the complete mirror through paginated inventory reads.

## Daily sequence

Run `scripts/brief/social_daily.py` from the deployed code checkout with `--project-root` pointing to the existing Abs By AI project, `--state-dir` pointing to a private directory outside every Git checkout, and `--live`. The worker uses the existing Blotato key for GET requests only. It imports, verifies approved photo twins, checks upcoming assets, writes `social-queue.json` and `migration-plan.json`, and reports its counts. The existing collector can read that queue path through `social_queue_snapshot` in its private configuration.

Run the same read-only review after the brief is assembled, then include the resulting seven-day queue in the signed edition. Import changed master records in bounded signed batches with the same edition text and hero provenance. Check matching publication receipts and stored readback. Source timestamps retain their actual collection times. Updating the queue does not refresh business text or establish a new priority.

The existing `publish_brief.py` accepts `--social-state-dir` to attach the fresh private queue and import the complete master export in signed batches without dropping entries. Add `--refresh-social-project` with the existing project root to run the read-only review after edition creation and immediately before validation and publication. All batches are validated before the first HTTP publication. A source older than 12 hours is rejected. The publisher never changes a Blotato schedule, even with these options.

The new top-up planner considers only explicitly approved content with exact authorized future dates inside the next 30 days. It never moves an expired date, fills an arbitrary free day, replaces media, deletes a post or corrects a queued release. It holds unknown content types, absent approval, stale or inaccessible media, account/time collisions, ads rejected by the existing guard and unverified TikTok covers. Capacity includes every existing queued platform entry, even outside the 30-day window. Excess eligible items are reported as overflow and remain in the master list.

The date-preserving daily entrypoint is `scripts/brief/social_topup.py`. Supply `--project-root`, `--state-dir` and `--authorization-file`. Without `--apply` it only writes a private dry run. Activation requires an enabled private authorization file and explicit confirmation. The October 8 policy is disabled because automatic approval review rejected the delegated activation authorization. The parent must obtain explicit human confirmation before enabling it or adding `--apply` to execution. Do not create another cron.

The policy freezes placement identities, including exact payload and date, to the 16 explicitly approved but never queued studio placements. The 38 previously queued approved placements are excluded so a later disappearance does not authorize replacement. New records, changed dates, captions or assets do not inherit this authorization. The planner remains general across platforms; this currently eligible cohort happens to contain Facebook photos only. Refresh private assets immediately before the top-up. Then refresh again for collection and publication. Existing entries beyond 30 days are reported in `existingOutsideWindow`, preserved and counted toward capacity.

The reusable reconciliation function acquires the inventory's process lock across all reads, creates and readbacks. It requires the reviewed plan digest, takes a fresh full schedule count and account/time collision check before every create, and records an uncertain submission before making a single non-retried POST. A timeout or failed readback stays held until reconciled. Successful creation requires a fresh schedule with the exact payload and date. Repeat runs do not repost confirmed placements. External writers do not share this lock; Blotato's own cap is the final account-wide guard.

## Release rules and evidence

New organic YouTube long-form releases are Sunday at 9 AM America/Chicago, at most one per week. A replacement counts as that week's release. The other platform copies cannot precede Monday at 9 AM and require verified public YouTube release. The planner reports violations and unknown first-release evidence. It does not fix them. Existing accepted posts, including the October 5 Facebook photo exception, are retained without a deletion or replacement recommendation. Photos are not subjected to the long-form cadence.

TikTok needs the approved tall cover embedded at frame zero and `videoCoverTimestamp: 0`. A zero timestamp alone does not prove the cover image or crop is correct. Follow `Docs/TIKTOK_COVERS.md` and the existing build verification before activation. No automatic cover rebuild or schedule replacement occurs here.

The calendar shows seven local Chicago dates, including the 23- and 25-hour DST days. Cover and video previews use authenticated same-origin requests. The media reader accepts only stored references on exact supported provider paths, does not follow redirects, supports a single byte range for inline iPad playback, and forwards no owner cookies or credentials upstream. Preview errors are visible and original-media links remain available to the owner.

Missing Facebook API cover fields do not prove a missing installed cover. A HEAD response proves availability only, not correct crop or visual match. Authentication failures, rate limits, old checks and inaccessible sources stay unverified. A confirmed 404 or 410 is reported as broken. Crop and asset identity remain unknown without specific evidence.

Public tile comparison is read-only. The private `public-tile-evidence.json` maps placement IDs to evidence identifying the exact public post, approved cover SHA-256, observed tile SHA-256, observation time and `public_profile_tile` surface. Equal observed bytes can establish a match. Different bytes alone cannot establish a mismatch because compression and grid crop can differ. A visual mismatch requires a recorded reviewer, normalized crop, assessment and reason. Wrong identity, stale evidence or unavailable platform access remains unknown. No correction, replacement or deletion is authorized by a finding.

`public_tiles.py` reads the documented [Blotato published-post list](https://help.blotato.com/rest-api-reference/publish-post/list-posts), including cursor pagination and exact public URLs. It joins a master placement only when account, platform and caption match uniquely and actual publication is within ten minutes of its authorized date. This tolerance accounts for service processing, not a different release day. It parses YouTube Shorts profile-grid renderers and TikTok profile ItemModule data. A watch-page OG image never qualifies as a grid cover. HTTP shells, authentication walls and unsupported markup remain unknown.

When HTTP does not provide the grid, an existing authorized browser session can inspect the profile and write `public-grid-observations.json` privately. Each observed tile needs `platform`, the exact `profileUrl` from `PROFILES`, `publicPostUrl`, the actual image `tileUrl`, `observedAt` and `surface: public_profile_tile`. Read DOM anchors and their corresponding loaded images on that profile. Do not guess CDN URLs, export cookies, or infer a grid from a detail player. Observations expire after 24 hours. The worker downloads the observed tile from an allowed provider without credentials or redirects, retains image bytes privately and computes SHA-256. It supports JPEG, PNG, WebP and AVIF.

The output includes a row for every recent published public URL, even if its approved-cover mapping is absent. `public-release-review.json`, `public-tile-candidates.json`, `public-profile-checks.json` and acquired evidence distinguish public URL availability, grid observation, image acquisition and cover comparison. A differing compressed tile goes to visual review; it is not an automatic mismatch. A reviewer can record a crop-normalized assessment in `public-tile-evidence.json`; both identity and newly acquired tile hash must agree before that assessment is accepted. None of this changes the post.

Native YouTube was reconnected by the user on October 8 with the existing upload and read-only scopes. `native_youtube.js` uses that existing local credential to obtain an access token in memory, pins channel `UC236gjadarHAhEhOMYNGJ9g`, enumerates the complete uploads playlist and reads video metadata in batches. Tokens never enter snapshots, stdout or the repository. It verifies recent Blotato public video IDs separately, distinguishes missing or wrong-channel results and deduplicates upload IDs. A failed read remains an explicit error, never a verified empty native queue. No credential file is changed and no video write endpoint is called.

The daily worker imports native scheduled videos as observed placements without approval. They appear in the master and seven-day calendar but are excluded from Blotato top-ups. Content type is inferred only from explicit short or long-form description markers. Installed native thumbnails are availability evidence, not approved-cover proof. Their stored signed YouTube CDN references are served behind the same owner gate with exact host, path and query-key restrictions. A private native video uses its Studio link because the API does not provide an original video file for inline playback. Scheduling collisions between native and Blotato queues require identity review rather than automatic deletion.

Historical cover association can use `approved-public-covers.json` privately. Each mapping identifies the exact platform and public video ID, approved asset SHA-256, source reference and explicit approval quote. Verify the local asset hash against the source receipt before adding it. Cover approval does not grant post or date approval. The October 7 Belly Fat Emergency handoff and RO-10 setup receipt provide two such exact associations. A long-form video outside the Shorts grid surface still requires its actual tile observation. RO-10's original is deliberately private, so it cannot receive a current public-tile match.

`expected-youtube-visibility.json` can record an exact video ID, expected status, source reference, explicit instruction quote and explanation. This distinguishes an intentional private original from an unexplained source conflict. The RO-10 receipt explicitly says to keep the original private and wait for the November 29 replacement. Unexpected visibility differences still appear as release alerts. An exception never publishes a video or changes its schedule. Other ambiguous historical associations remain unknown.

Public profile access on YouTube Shorts, TikTok, Facebook and Instagram must still be separately observed; successful native API access does not establish a visual match. Unavailable checks do not become invented matches.
